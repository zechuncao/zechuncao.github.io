Hashing: Basic Plan

Save items in a key-indexed table, where the index is a function of the key.

Hash function. Method for computing an array index from a key.

Ideal Hashing

With a hash function and no collisions, neither dictionary operation searches:

public void add(K key, V value)
{  hashTable[hash(key)] = value;  }

public V getValue(K key)
{  return hashTable[hash(key)];  }

Chapter 5 searched for the key before storing it, and no implementation did that in less than \(O(n)\). Each line here is a constant number of operations.

Hash Functions

Computing the Hash Function Must Know

Idealistic goal. Scramble the keys uniformly to produce a table index.

  • Efficiently computable.
  • Each table index equally likely for each key.
  • The same index every time for a given key.

The third is what makes a later search find the entry: getValue looks in one slot, and it has to be the slot add computed.

A thoroughly researched problem, still problematic in practical applications.

  • Bad. First three digits.
  • Better. Last three digits.

Practical challenge. Need a different approach for each key type.

Java’s Hash Code Conventions

All Java classes inherit a method hashCode(), which returns a 32-bit int.

Requirement. If x.equals(y), then x.hashCode() == y.hashCode().

Highly desirable. If !x.equals(y), then x.hashCode() != y.hashCode().

Break the requirement and a search for a key that is in the table computes a different index than the add did, and reports that the key is absent.

Four Kinds of Implementation

  • Default implementation. Memory address of x.
  • Legal (but poor) implementation. Always return 17.
  • Customized implementations. Integer, Double, String, File, URL, Date, …
  • User-defined types. Users are on their own.

The default breaks the requirement for two equal strings, which is why String replaces it. return 17; keeps the requirement and gives every key one index.

Integers, Booleans and Doubles

public int hashCode()                 // Integer
{  return value;  }

public int hashCode()                 // Boolean
{
   if (value) return 1231;
   else       return 1237;
}

public int hashCode()                 // Double
{
   long bits = doubleToLongBits(value);     // IEEE 64-bit representation,
   return (int) (bits ^ (bits >>> 32));     // high 32 bits xor low 32 bits
}

An int key is its own hash code, and a byte, short or char casts to one. For those keys step 1 does nothing, and the whole hash function is the compression.

Strings Must Know

public int hashCode()                 // Java library implementation
{
   int hash = 0;
   for (int i = 0; i < length(); i++)
      hash = s[i] + (31 * hash);      // ith character of s
   return hash;
}
  • Horner’s method to hash a string of length \(L\): \(L\) multiplies and adds.
  • Equivalent to \(h = s_0 \cdot 31^{\,L-1} + \cdots + s_{L-2} \cdot 31 + s_{L-1}\).

Horner’s Method

Ex. String s = "call"; int code = s.hashCode();

Each character of "call" counts as its Unicode value, and the running value is multiplied by 31 at every one of them.

The nesting is Horner’s method, and it is the polynomial \[3{,}045{,}982 = 99 \cdot 31^3 + 97 \cdot 31^2 + 108 \cdot 31 + 108.\]

Question

'c' is 99, 'a' is 97 and 't' is 116.

What is "cat".hashCode()?

  • A 312
  • B 3,282
  • C 98,262
  • D 114,582

\(99 \cdot 961 + 97 \cdot 31 + 116 = 98{,}262\). 312 adds the three values and ignores position, 3,282 is \(3166 + 116\), which drops the multiply at the last character, and 114,582 is "tac".

Performance Optimization

  • Cache the hash value in an instance variable.
  • Return the cached value.
public int hashCode()
{
   int h = hash;                      // return cached value
   if (h != 0) return h;
   for (int i = 0; i < length(); i++)
      h = s[i] + (31 * h);
   hash = h;                          // store cache of hash code
   return h;
}

User-Defined Types

public final class Transaction implements Comparable<Transaction>
{
   private final String who;
   private final Date   when;
   private final double amount;
   ...
   public int hashCode()
   {
      int hash = 17;                                   // nonzero constant
      hash = 31*hash + who.hashCode();                 // reference type
      hash = 31*hash + when.hashCode();
      hash = 31*hash + ((Double) amount).hashCode();   // primitive: wrapper
      return hash;                                     // 31: a small prime
   }
}

Hash Code Design Must Know

A standard recipe for user-defined types.

  • Combine each significant field using the \(31x + y\) rule.
  • If the field is a primitive type, use the wrapper type’s hashCode().
  • If the field is null, return 0.
  • If the field is a reference type, use hashCode(), which applies the rule recursively.
  • If the field is an array, apply the rule to each entry, or use Arrays.deepHashCode().

In Practice, In Theory

In practice. The recipe works reasonably well, and is used in the Java libraries.

In theory. Keys are bitstrings, and “universal” hash functions exist.

Basic rule. Need to use the whole key to compute the hash code.

A function that reads the first field only gives one index to everyone named Maria.

Modular Hashing

Hash code. An int between \(-2^{31}\) and \(2^{31} - 1\).

Hash function. An int between 0 and \(n - 1\), for use as an array index, where \(n\) is the table size and is typically a prime.

Step 2 is the only place the table size appears. Change \(n\) and every index changes, while no hash code does.

Why the Table Size Is Prime

Compression with % keeps a remainder, so a size sharing a factor with the keys leaves slots unreachable. Eight keys, all multiples of 4:

\(k\) 4 8 12 16 20 24 28 32
\(k \bmod 12\) 4 8 0 4 8 0 4 8
\(k \bmod 13\) 4 8 12 3 7 11 2 6

A size of 12 holds the eight in three slots, because \(\gcd(4, 12) = 4\); an even size does it to every even key. A prime shares no factor, so 13 gives each key its own slot. This chapter’s tables hold 13 and 17.

Three Versions of hash()

private int hash(Key key)
{  return key.hashCode() % n;  }                   // bug

private int hash(Key key)
{  return Math.abs(key.hashCode()) % n;  }         // 1-in-a-billion bug

private int hash(Key key)
{  return (key.hashCode() & 0x7fffffff) % n;  }    // correct

% keeps the sign of its left operand, so the first can return a negative index. Math.abs(-2147483648) is -2147483648, because \(2^{31}\) is not an int, and "polygenelubricants" has exactly that hash code. The third clears the sign bit.

Compressing a Hash Code Must Know

The textbook tests the sign instead of clearing the bit, and writes the table size as hashTable.length:

private int getHashIndex(K key)
{
   int hashIndex = key.hashCode() % hashTable.length;
   if (hashIndex < 0)
      hashIndex = hashIndex + hashTable.length;

   return hashIndex;
}

Adding the table length to a negative remainder brings it into range without changing which slot it names. "Rivera" has hash code \(-1{,}846{,}791{,}179\), so % gives \(-12\), and the if makes it 1.

Question

A key’s hashCode() returns \(-45\), and the table has 13 slots.

Which index does getHashIndex return?

  • A −6
  • B 7
  • C 6
  • D −3

-45 % 13 is -6, and -6 + 13 is 7. −6 is the answer without the if, 6 is 45 % 13, the remainder of the code made positive first, and −3 is -45 / 13.

Hash Value Frequencies

Java’s String data uniformly distribute the keys of A Tale of Two Cities: every one of the 97 slots takes between 90 and 135 of the 10,615 distinct words, against an even share of 109.

Collision Resolution

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Resolving Collisions Must Know

Two different keys collide when the hash function computes one index for both. The location the new key reaches already holds an entry, and both entries belong in the dictionary.

Two choices:

  • Store the new entry in another location of the table. That is open addressing.
  • Change the table so that one location holds more than one entry. That is separate chaining.

Neither choice changes the hash function. There are more possible keys than there are slots, so collisions happen whatever the function is.

Resolving Collisions

A table of 13 slots, with \(H(k) = k \bmod 13\) and one entry in it.

Slot 5 holds the entry whose key is 18, because H(18) = 5.

Question

Slot 5 holds the entry whose key is 18, and add(18, value) is called with a new value for that same key.

Is that a collision?

  • A Yes, the slot is occupied.
  • B Yes, two adds, one location.
  • C No, the keys are equal.
  • D No, add ignores the location.

A collision needs two different keys at one index. Equal keys mean one entry, so the entry count does not change.

Collision Resolution

Linear Probing

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Linear Probing Must Know

On a collision, examine the next location of the table, and keep going until a free one turns up. The locations examined are the probe sequence:

\[(H(k) + j) \bmod n, \qquad j = 0, 1, 2, \dots\]

  • \(j = 0\) is the home index \(H(k)\) itself, and \(n\) is the table size.
  • Reducing mod \(n\) makes the table circular: the location after \(n - 1\) is 0.
  • The walk stops at the first free location, or at the key itself, which makes the call a replacement.

Tracing Linear Probing

The first three keys go in, one click each.

Question

Three keys are in, and the next key is 59.

Which slot does add(59) put it in?

  • A 7
  • B 8
  • C 4
  • D 0

44 is in slot 7, so 59’s home index is taken and the probe moves on to 8. 7 takes the home index to be free, 4 probes backwards, and 0 takes the first free location in the table, not in the sequence.

The Probe Sequences Must Know

key \(H(k)\) probes slot
18 5 5 5
31 5 5 → 6 6
44 5 5 → 6 → 7 7
59 7 7 → 8 8
12 12 12 12
25 12 12 → 0 0

Six keys cost five probes beyond their home indices. Four of the six collided, and 59 collided with 44, which is not stored at its own home index.

Clustering

Linear probing leaves the occupied locations in runs. Each run is a cluster, and a key whose home index is inside one probes every location to the end of it.

  • The six keys left two clusters: slots 5 to 8, and slots 12 and 0, which are neighbours in a circular table.
  • A key hashing to 5, 6, 7 or 8 now lands in slot 9, and that cluster grows by one.

This is primary clustering: keys with different home indices end up on one probe sequence.

Searching a Probe Sequence Must Know

A search runs the probe sequence the insertion ran, and ends in one of three ways.

  • The location holds the key. Found.
  • The location is empty. Not found: nothing has ever been stored there, so no insertion can have walked past it.
  • The sequence returns to the home index. The table is full and the key is not in it.

A search that misses examines every location of the cluster it starts in.

Question

The six keys are in the table, 83 is not one of them, and \(H(83) = 83 \bmod 13 = 5\).

How many locations does a search for 83 examine?

  • A 1
  • B 4
  • C 6
  • D 5

83 is compared with 18, 31, 44 and 59, and the empty slot 9 ends the search. 4 leaves out that last location, 6 goes one past it, and 1 stops at the home index.

Removing an Entry

This is the table the linear-probing trace left. One entry comes out of it, and the location it held is set to null.

The table the linear-probing trace left.

Three Kinds of Location Must Know

A removal cannot write null into the location it empties, because a search that reached it would stop there. So a location is one of three things.

  • Occupied. It holds an entry of the dictionary.
  • Empty. It holds null and always has.
  • Available. Its entry was removed.

A search steps over an available location and stops only at an empty one. An insertion may reuse an available location, but only once it has searched the whole sequence for the key it is adding.

Marking a Location Available

The same removal, with the location it empties marked available.

The table the linear-probing trace left.

Question

Slot 6 is available, 57 is not in the table, and \(H(57) = 5\).

Where does add(57, value) store it?

  • A 6
  • B 9
  • C 5
  • D 1

The insertion walks to slot 9 first, because a 57 stored anywhere along the sequence would make the call a replacement. None turns up, so it goes back to the first available location. 9 is the first empty location, which leaves the hole unused.

Quadratic Probing

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Quadratic Probing Must Know

Add the square of the probe number to the home index:

\[(H(k) + j^2) \bmod n, \qquad j = 0, 1, 2, \dots\]

  • The offsets are 0, 1, 4, 9, 16, …, so the sequence leaves the neighbourhood of the home index after two probes.
  • It never fills consecutive locations, so a key whose home index is next to a cluster does not have to probe through it.

With \(n\) prime the offsets reach \(\lceil n/2 \rceil\) distinct locations and then repeat. For \(n = 13\) that is 7 of the 13 slots, so the table has to stay at most half full for an insertion to be sure of one.

Tracing Quadratic Probing

Secondary Clustering

18, 31 and 44 share a home index, and each one walked the start of the same sequence, 5, 6, 9, stopping at the first free location.

Quadratic probing spreads one probe sequence out, and every key with that home index follows the same sequence. That is secondary clustering.

  • Linear probing: keys with different home indices end up on one probe sequence.
  • Quadratic probing: only keys with the same home index do.

Double Hashing

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Double Hashing Must Know

A second hash function computes the step between probes, so the step depends on the key:

\[(H_1(k) + j \cdot H_2(k)) \bmod n, \qquad j = 0, 1, 2, \dots\]

with \(H_1(k) = k \bmod 13\) and \(H_2(k) = 7 - (k \bmod 7)\).

\(H_2\) returns 1 through 7, never 0, and a step of 0 would probe the home index forever. Every step from 1 to 7 is coprime with 13, so a sequence reaches all 13 slots.

Linear and quadratic probing add the same offsets to every key. This is the first method whose probe sequence depends on the key.

Tracing Double Hashing

The first two keys. 18 lands on its first probe and never uses its step.

A table of 13 slots, H(k) = k mod 13, and the keys 18, 31, 44, 59, 12, 25 added in that order.

Question

18 and 31 are in. The next key is 44, and \(44 \bmod 7 = 2\).

Which slot does 44 take?

  • A 6
  • B 7
  • C 9
  • D 10

\(H_2(44) = 7 - 2 = 5\), so the sequence is 5, 10, 2, … and slot 10 is free. 6 adds 1 like linear probing, 7 adds \(44 \bmod 7\) rather than \(7 - (44 \bmod 7)\), and 9 reuses the step 31 was given.

Comparing the Three Methods

The same six keys, three times over: one table per method.

Which Clustering Each Method Has

  • Linear probing has primary clustering: keys with different home indices end up on one probe sequence, and the run grows.
  • Quadratic probing removes primary clustering and keeps secondary clustering. Only keys with the same home index share a sequence.
  • Double hashing removes both, because the step comes from the key.

59 hashed to 7, and kept slot 7 in the two tables that removed primary clustering. 18, 31 and 44 share a home index, and only double hashing sent them to three different slots.

Separate Chaining

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Separate Chaining Must Know

Separate chaining changes the table instead of the probe sequence. Each location is a bucket: a chain of linked nodes holding every entry whose key hashes to that index.

  • add links a new node at the head of the chain, which costs the same whatever the chain already holds.
  • No entry is ever stored away from its home index, so there is no probe sequence and no available state.
  • The load factor can pass 1. A bucket holds as many entries as hash to its index.

Tracing Separate Chaining

The same six keys go in again, each linked into the chain at its own home index.

A table of 13 slots. Each one is a bucket: a chain of linked nodes, empty to begin with.

The Chains

index chain (head → tail)
5 44 → 31 → 18
7 59
12 25 → 12

The other ten buckets are empty.

Linking at the head puts the newest key first, so a chain reads in reverse insertion order. Six keys fill three of the 13 buckets, and the longest chain holds three of them.

Searching and Removing a Chain

getValue hashes the key, then compares it with the keys of one chain, in order, until it matches or the chain ends.

  • A search examines one chain and no other part of the table.
  • A miss on an empty bucket costs no comparison at all.
  • remove unlinks a node from its chain, and no other key’s search runs through that node.

Open addressing needs the available state because a key can sit far from its home index. Here every key is in the chain of its own index.

Open Addressing or Chaining

open addressing separate chaining
an entry sits anywhere in it in its own chain
a search walks a probe sequence one chain
a removal marks it available unlinks a node
memory the array alone a node per entry
entries it holds one per location no fixed limit

Both keep a search short as long as the hash function spreads the keys; neither helps a function that sends every key to one index.

Part 3

Implementing a Dictionary with Hashing

hash functions · collisions · linear probing · quadratic probing · double hashing · separate chaining · the dictionary class

Four Operations, Two Costs

Every dictionary operation begins by searching for the key, so each one costs what that search costs.

the call the key is there the key is not there
getValue successful unsuccessful
contains successful unsuccessful
remove successful unsuccessful
add successful, and replaces unsuccessful, and stores

Two costs fill the whole table. The common case for add is a key that is not there, so storing a new entry costs the unsuccessful search: the probe sequence has to come back empty before the entry can go in.

Load Factor Must Know

\[\lambda = \frac{\text{number of entries in the dictionary}}{\text{number of locations in the hash table}}\]

  • \(\lambda\) is never negative, and it is 0 for an empty dictionary.
  • With open addressing every entry is in the array, so \(\lambda \le 1\).
  • With separate chaining \(\lambda\) has no maximum. It is the average length of a chain.

Part 2’s table holds six entries in 13 slots, so \(\lambda = 6/13 \approx 0.46\).

The Cost of a Search Must Know

Average number of comparisons, in terms of \(\lambda\):

method a search that fails a search that succeeds
linear probing \(\tfrac12\bigl[1 + 1/(1-\lambda)^2\bigr]\) \(\tfrac12\bigl[1 + 1/(1-\lambda)\bigr]\)
quadratic, double hashing \(1/(1-\lambda)\) \(-\ln(1-\lambda)/\lambda\)
separate chaining \(\lambda\) \(1 + \lambda/2\)

Every formula is in \(\lambda\) alone. The cost of a search is independent of the table size \(n\): it depends on how full the table is, not on how big it is.

What the Formulas Say

Average probes against the load factor, from the formulas above.

Open Addressing by the Numbers

\(\lambda\) 0.1 0.3 0.5 0.7 0.9
linear, fails 1.1 1.5 2.5 6.1 50.5
linear, succeeds 1.1 1.2 1.5 2.2 5.5
quadratic and double, fails 1.1 1.4 2.0 3.3 10.0
quadratic and double, succeeds 1.1 1.2 1.4 1.7 2.6
  • A search that succeeds stays cheap in both. It stops at the key it finds.
  • A search that fails is the one that grows with the load factor.
  • At \(\lambda = 0.9\): linear probing averages 50.5 comparisons, the other two 10.0.

Separate Chaining by the Numbers

\(\lambda\) 0.5 1.0 1.5 2.0 4.0
a search that fails 0.5 1.0 1.5 2.0 4.0
a search that succeeds 1.3 1.5 1.8 2.0 3.0

Nothing breaks when \(\lambda\) passes 1, because no chain has to fit inside the array. The cost grows with \(\lambda\) instead of exploding, which is why chaining is the scheme that tolerates a crowded table.

Keeping the Load Factor Down Must Know

  • Open addressing: keep \(\lambda \le 0.5\).
  • Separate chaining: keep \(\lambda \le 1.0\).

A dictionary cannot refuse an entry to stay inside those bounds, so it does the other thing: when an addition pushes \(\lambda\) past the limit, the table grows.

Rehashing Must Know

Growing the table takes three steps.

  1. Compute the new size: double the present size, then move up to the next prime.
  2. Allocate a new array of that size.
  3. Add every current entry again, with add, into the new array.

Step 3 is the expensive one, and it is not optional. An index is computed from the table size, so an entry copied slot-for-slot would sit at an index no search would compute for it.

Question

A table of 17 locations has grown too full.

What size does it grow to?

  • A 34
  • B 37
  • C 19
  • D 35

\(2 \times 17 = 34\), and 34, 35 and 36 are all composite, so the next prime is 37. 34 stops before the prime, 19 is the next prime after 17 and does not double, and 35 is \(5 \times 7\).

Growing the Table

The linear-probing table from Part 2: 6 entries in 13 slots.

What the Resize Cost

Seven add calls ran to move seven entries, and each one hashed its key again. One addition out of the seven paid for all of it.

  • A location in the available state holds no entry, so it is skipped. Rehashing clears every tombstone the table had collected.
  • Only 12 kept the index it had. An index is \(k \bmod n\), and \(n\) changed.

The load factor drops from 0.54 to 0.24, so the next resize is a long way off. Spread over the additions between them, the cost of growing is constant per addition.

A Hash Table of Entries

The array does not hold keys. A location holds null, the shared AVAILABLE entry, or a reference to an entry object. Search key and the value are stored together.

The Entry Class

protected final class Entry<S, T>
{
   private S key;
   private T value;

   private Entry(S searchKey, T dataValue)
   {
      key = searchKey;
      value = dataValue;
   }
   // getKey, getValue and setValue go here
}

One object stands for the available state, and every location a removal empties refers to that same object. So Part 2’s three kinds of location are three outcomes of reading one array element: null, AVAILABLE, or an entry.

The Class HashedDictionary

   protected final Entry<K, V> AVAILABLE = new Entry<>(null, null);

   public HashedDictionary()
   {
      this(DEFAULT_CAPACITY);
   }

MAX_LOAD_FACTOR is the 0.5 of the rule, written down once. Every add compares against it.

The Constructor

   public HashedDictionary(int initialCapacity)
   {
      initialCapacity = checkCapacity(initialCapacity);
      numberOfEntries = 0;

      // the size is the capacity asked for, raised to a prime
      int tableSize = getNextPrime(initialCapacity);
      checkSize(tableSize);

      @SuppressWarnings("unchecked")
      Entry<K, V>[] temp = (Entry<K, V>[])new Entry[tableSize];
      hashTable = temp;
   }

A caller asking for 20 locations gets 23. The table size is never the number the caller gave unless that number is already prime.

getValue

public V getValue(K key)
{
   V result = null;
   int index = getHashIndex(key);          // probes, and returns where key is

   if ((hashTable[index] != null) && (hashTable[index] != AVAILABLE))
      result = hashTable[index].getValue();

   return result;                          // null if the key is not there
}

Chapter 5’s getValue walked the structure. This one computes an index and reads one location, and returns null the same way.

Question

getValue again, with the declarations left out:

int index = getHashIndex(key);

if ((hashTable[index] != null) && (hashTable[index] != AVAILABLE))
   result = hashTable[index].getValue();

There is no loop here. Where did the probing go?

  • A Nowhere; one read is all it needs.
  • B Into getHashIndex.
  • C Into hashCode.
  • D Into the array itself.

getHashIndex computes the home index, then follows the probe sequence until it finds the key or an empty location. Part 1’s version only compressed a hash code.

remove

public V remove(K key)
{
   V removedValue = null;
   int index = getHashIndex(key);

   if ((hashTable[index] != null) && (hashTable[index] != AVAILABLE))
   {
      removedValue = hashTable[index].getValue();
      hashTable[index] = AVAILABLE;             // not null
      numberOfEntries--;
   }

   return removedValue;
}

One assignment does the removal, and it writes AVAILABLE rather than null. That is the whole of Part 2’s rule in code.

add Must Know

public V add(K key, V value)
{
   V oldValue;
   int index = getHashIndex(key);

   if ((hashTable[index] == null) || (hashTable[index] == AVAILABLE))
   {
      hashTable[index] = new Entry<>(key, value);   // key was not there
      numberOfEntries++;
      oldValue = null;
   }
   else
   {
      oldValue = hashTable[index].getValue();       // key was there
      hashTable[index].setValue(value);
   }

   if (isHashTableTooFull())
      enlargeHashTable();

   return oldValue;
}

Reading add

The two branches are Chapter 5’s two outcomes, unchanged: a new key is stored and null comes back, and a key already present has its value replaced and the old value comes back.

The resize check is last, and it runs on every addition, including the one that only replaced a value. That costs a comparison and is what keeps \(\lambda\) inside the bound.

enlargeHashTable

private void enlargeHashTable()
{
   Entry<K, V>[] oldTable = hashTable;
   int oldSize = hashTable.length;
   int newSize = getNextPrime(oldSize + oldSize);

   @SuppressWarnings("unchecked")
   Entry<K, V>[] temp = (Entry<K, V>[])new Entry[newSize];
   hashTable = temp;
   numberOfEntries = 0;              // add will count them again

   for (int index = 0; index < oldSize; index++)
   {
      if ((oldTable[index] != null) && (oldTable[index] != AVAILABLE))
         add(oldTable[index].getKey(), oldTable[index].getValue());
   }
}

hashTable is reassigned before the loop, so each add writes into the new array while the loop reads the old one.

Iterating a Hash Table

An iterator walks the array from index 0 and returns the key in every location that holds a current entry, skipping the empty ones and the available ones.

The order is the array’s, so it depends on the hash function and on the order collisions were resolved in. It is not the order the entries were added in, and it is not sorted.

Java’s HashMap Must Know

java.util.HashMap is the dictionary of Chapter 5, implemented by hashing.

  • Each location is a bucket that holds several entries, so it resolves collisions by chaining.
  • The default maximum load factor is 0.75, and the default table holds 16 buckets.
  • Passing the number of buckets to the constructor avoids resizing a table whose size you can predict.

It doubles rather than moving to the next prime: its sizes are powers of two, and it compresses a hash code with a bit mask instead of %.

Question

A HashMap is created with 32 buckets and the default maximum load factor of 0.75. Entries with distinct keys are added one at a time.

Which addition is the first to resize the table?

  • A the 25th
  • B the 24th
  • C the 32nd
  • D the 16th

\(32 \times 0.75 = 24\) entries is the threshold, so the 24th addition fits and the 25th passes it. The new table holds 64 buckets.

Java’s HashSet

java.util.HashSet implements java.util.Set, and it holds an instance of HashMap to do it.

A set is a dictionary with the values thrown away: every element is stored as a key, mapped to one shared placeholder object. contains is containsKey, and it costs what a HashMap search costs.

The worst case is every key at one index, searched from the front.

What It Cost

Hashing gives up two things the other four implementations had.

  • Order. Nothing comes out sorted, and no operation asks a key to compare with another. compareTo is replaced by hashCode.
  • Space. The table is kept half empty on purpose, and it is rebuilt whenever it fills.

Chapter 7 keeps the order and gives up the constant: a search tree compares keys, returns them sorted, and costs \(O(\log n)\).
