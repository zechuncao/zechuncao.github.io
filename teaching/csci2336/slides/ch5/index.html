Looking Up a Number

A phone directory holds thousands of entries. You want the number that goes with one name.

Every structure so far answers a different question. A stack hands back the entry that arrived last. A queue hands back the entry that arrived first. An array hands back the entry at index 7.

None of them can be asked for the entry that goes with “Rivera”.

Part 1

The Dictionary

Key, Not Position Must Know

A dictionary stores entries. Each entry is a key and the value that goes with it.

list dictionary
what you supply a position a search key
what you get back the entry at that position the value for that key
duplicates allowed keys are unique
order of the entries the order you put them in not promised at all

There is no getEntry(position). Access is always through the key.

The Operations

V       add(K key, V value)
V       remove(K key)
V       getValue(K key)
boolean contains(K key)
Iterator<K> getKeyIterator()
Iterator<V> getValueIterator()
boolean isEmpty()
int     getSize()
void    clear()

add on a key that is already present replaces the value. Keys stay unique, so a dictionary never grows two entries with the same key.

What add Returns Must Know

A dictionary maps student IDs to names.

call returns contents afterwards
d.add(140, "Ben") null {140→Ben}
d.add(207, "Mia") null {140→Ben, 207→Mia}
d.add(140, "Cal") "Ben" {140→Cal, 207→Mia}
d.remove(315) null unchanged
d.getValue(207) "Mia" unchanged

null is the answer to two questions: was this key already here? and is this key here at all? That is why neither a key nor a value may be null — a stored null would make “absent” and “present, with value null” the same answer.

Question

d holds the entry ("red", 3).

What does d.add("red", 7) return, and what does d hold afterwards?

  • A true; {red→3, red→7}
  • B null; {red→7}
  • C 3; {red→7}
  • D throws an exception

The old value comes back so the client can tell a replacement from a new entry. A second ("red", …) entry is not possible.

Counting Words

Read words one at a time; the key is the word, the value is how many times it has been seen.

while (data.hasNext()) {
   String nextWord = data.next().toLowerCase();
   Integer frequency = wordTable.getValue(nextWord);
   if (frequency == null)
      wordTable.add(nextWord, 1);
   else
      wordTable.add(nextWord, frequency + 1);
}

On we can do this and we can do more: nine words read, so nine add calls. Six return null and create an entry; three return a count and replace it. The table ends with six entries, we→2, can→2, do→2, this→1, and→1, more→1.

Part 2

Four Implementations

Four Places for an Entry

The entries can sit in an array or in a linked chain, and either one can be kept in key order or left alone.

unsorted sorted by key
array append at the end binary search, then shift
linked chain add at the head walk to the spot, then relink

All four answer the same questions. They disagree about which operation is cheap, and that is the whole decision.

The Unsorted Array

Entries sit wherever they landed. A key says nothing about where it is.

7 entries, sitting in the order they arrived.

A failed search is the worst case: only reaching the end proves a key is absent. A successful one compares \((n + 1)/2\) keys on average — 4 of these 7.

Binary Search Must Know

Keep the array in key order and getValue can halve the window instead of walking it. mid = (low + high) / 2, integer division.

A sorted array of 10 keys, and the search for 72 has not started.

Three comparisons, where a sequential walk of the same ten keys would have made nine.

When the Key Is Absent

The same array, and a key it does not hold.

A sorted array of 10 keys, and the search for 60 has not started.

The search ends holding something useful, and add uses it to find where a new entry belongs. Ten keys need at most 4 comparisons, 50 keys at most 6, and 1,000 keys at most 10.

Making Room Must Know

Binary search finds the spot in \(O(\log n)\). Putting the entry there is the expensive half: every larger entry moves one slot right.

An empty sorted array. The keys arrive in this order: 25, 60, 14, 38, 7.

Order of Arrival

Seven shifts for five keys. A key that lands at the front moves everything ahead of it; a key that lands at the end moves nothing.

Eight keys arriving in ascending order cost 0 shifts in all. The same eight arriving in descending order cost \(0 + 1 + \cdots + 7 = 28\), which is \(n(n-1)/2\).

Binary search found the spot in \(O(\log n)\) in every one of those adds. The shifting is what makes add \(O(n)\).

Search First Must Know

Linking a node at the head costs one assignment, so this add looks like an \(O(1)\) operation.

An unsorted chain of 3, and 33 to add.

The head insertion really is \(O(1)\). The search in front of it is what makes the operation \(O(n)\).

The Sorted Chain

The walk moves on while key.compareTo(currentNode.getKey()) > 0, so it stops at the first node whose key is not smaller.

A sorted chain, and 30 to add.

Reverse those two lines and the rest of the chain is unreachable. Nothing shifts here, but nothing can be halved either: getValue still walks.

Part 3

Choosing One

The Four Costs Must Know

Worst case, \(n\) entries.

operation unsorted array sorted array unsorted chain sorted chain
add \(O(n)\) \(O(n)\) \(O(n)\) \(O(n)\)
getValue \(O(n)\) \(O(\log n)\) \(O(n)\) \(O(n)\)
remove \(O(n)\) \(O(n)\) \(O(n)\) \(O(n)\)
traverse \(O(n)\) \(O(n)\) \(O(n)\) \(O(n)\)

Reading the Table

Every add is \(O(n)\). Keys are unique, so the key has to be looked for before the entry can be stored, and that search is the same walk getValue makes.

remove is \(O(n)\) for the same reason: the entry has to be found before it can be taken out, and only the sorted array finds it faster than a walk.

Linking a node at the head costs one assignment, and appending to an unsorted array costs one more. Both are \(O(1)\), and neither changes the order of growth of the operation around it.

Retrieval is the only row where the four disagree, and the sorted array is the only one that beats a walk.

Question

A spell checker loads a fixed word list once when it starts, then answers millions of contains queries and never adds another word.

Which implementation fits?

  • A Unsorted array
  • B Sorted array
  • C Unsorted chain
  • D Sorted chain

The expensive operation is the one that happens once. Sorting the word list costs \(O(n \log n)\) at startup; after that every query is \(O(\log n)\). A chain cannot binary search, and the unsorted array makes every query a walk.

Java’s Map

java.util.Map is this ADT under different names: put for add, get for getValue, containsKey for contains. put and remove return the previous value, or null.

Map<Integer, Integer> m = new TreeMap<>();
int[] data = {4, 8, 4, 2, 8, 8};
for (int i = 0; i < data.length; i++)
   m.put(data[i], i);
System.out.print(m + " " + m.size());

Prints {2=3, 4=2, 8=5} 3. Each key keeps the last index it was given, because put replaces; TreeMap is a sorted dictionary, so the keys come out in ascending order.

What Hashing Must Beat

Four implementations, and every one of them is \(O(n)\) for add and remove. The best search any of them offers is \(O(\log n)\).

Searching has been the same move every time: compare the target with a stored key, and use the answer to decide where to look next. Binary search just makes that decision well.
