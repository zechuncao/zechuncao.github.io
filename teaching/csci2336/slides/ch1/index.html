Guess My Number

I am thinking of a whole number between \(1\) and \(1{,}000{,}000\).

  • You guess. I answer higher or lower.
  • You keep guessing until you get it.

How many guesses do you need to be certain — no luck involved?

Twenty

Each guess throws away half of what is left.

\[1{,}000{,}000 \;\to\; 500{,}000 \;\to\; 250{,}000 \;\to\; \cdots \;\to\; 1\]

Twenty halvings is enough, because \(2^{20} = 1{,}048{,}576\).

That Gap Is the Whole Course

Some algorithms behave like the guessing game — a thousand times the problem costs ten more steps. That is the good case.

Others are the opposite. Doubling the input multiplies the work, and a few doublings later the program stops finishing at all.

Today: how to tell the two apart — before your users tell you.

Who Is Asking

Why Analyze an Algorithm?

  • Predict performance. Will this finish before the demo?
  • Compare algorithms. Which of the two should I ship?
  • Provide guarantees. What can I promise a customer?
  • Understand the theory. Why can nobody do better?

The first three are this course. The fourth is a course of its own.

The practical reason: avoid performance bugs. The code is correct, every test passes, and it is unusable at real size.

Brute Force

public class ThreeSum
{
   public static int count(int[] a)
   {
      int N = a.length;
      int count = 0;
      for (int i = 0; i < N; i++)              // check each triple
         for (int j = i+1; j < N; j++)         // (ignore integer overflow)
            for (int k = j+1; k < N; k++)
               if (a[i] + a[j] + a[k] == 0)
                  count++;
      return count;
   }
}

It is obviously correct. Is it fast enough?

What Sets the Running Time?

Two independent things.

The algorithm. How the number of steps grows as \(N\) grows — one loop, two loops, three.

The machine. How long a single step takes — a few nanoseconds, fixed by the hardware you run on.

Guess a shape with one unknown for each:

\[T(N) = a \cdot N^{b}\]

\(a\) belongs to the machine, \(b\) to the algorithm. We want \(b\).

The Ratio Is the Exponent

\(N\) time (s) ratio
\(500\) \(0.030\) —
\(1{,}000\) \(0.207\) \(6.9\)
\(2{,}000\) \(1.643\) \(7.9\)
\(4{,}000\) \(13.207\) \(8.0\)
\(8{,}000\) \(105.326\) \(8.0\)

We cannot measure \(b\) directly. But we can double \(N\) and divide:

\[\frac{T(2N)}{T(N)} = \frac{a\,(2N)^{b}}{a\,N^{b}} = 2^{b}\]

The machine’s constant \(a\) cancels. What is left measures \(b\) alone.

Our ratio settles at \(8 = 2^{3}\), so \(b = 3\). 3-Sum is cubic — measured, not read off the code.

Why Isn’t the First Ratio 8?

The first ratio is \(6.9\), not \(8\). At \(N = 500\) the whole run takes \(0.030\) seconds.

  • Java is still compiling. That same call takes \(0.028\) s the first time and \(0.006\) s once the JIT has optimized it — five times faster, identical code.
  • Fixed costs dominate. Allocating the array and reading the clock are a big slice of \(0.030\) s and nothing at all of \(105\) s.

The early rows are not measuring the algorithm.

Read the Bottom of the Table

The ratios converge. Take \(b\) from where they settle, not from the first row.

The rule is a claim about large \(N\) — small \(N\) is where the machine, not the algorithm, is doing the talking.

And if they never settle? Then it is not a power law, and the method does not apply.

Bad news. Precise measurements are hard to get. Good news. Cheaper than in any other science — run a hundred experiments before lunch.

Predict, Then Verify

The rule. Ratio \(8\) means every doubling costs \(8\times\).

Predict. \(N = 4{,}000\) took \(13.207\) s, so \(N = 8{,}000\) should take about \(13.207 \times 8 = 105.7\) s.

Observe. The \(8{,}000\) run we started earlier: \(105.3\) seconds.

Within half a percent — from a number we never measured.

Want the constant too? \(105.326 = a \times 8000^{3}\) gives \(a = 2.06 \times 10^{-10}\).

What Transfers, What Doesn’t

The constant \(a\)

  • Hardware — CPU, cache
  • Software — compiler, JVM
  • System — OS, other apps

The exponent \(b\)

The algorithm.

Nothing else.

Run this on your laptop: \(a\) will differ, \(b\) will still be \(3\).

That is why we compare with big O, not stopwatches.

Total running time: sum of cost × frequency for all operations.

  • Need to analyze the program to determine the set of operations.
  • Cost depends on the machine and the compiler.
  • Frequency depends on the algorithm and the input data.

In principle, accurate mathematical models are available.

In practice, you measure — and we did. Now we count.

“ It is convenient to have a measure of the amount of work involved in a computing process, even though it be a very crude one. We may count up the number of times that various elementary operations are applied in the whole process and then given them various weights. Simplification 2: Tilde Notation

  • Estimate running time (or memory) as a function of \(N\).
  • Ignore lower-order terms — negligible when \(N\) is large, and when \(N\) is small we do not care.
Ex 1. \(\tfrac{1}{6}N^3 + 20N + 16\) \(\sim \tfrac{1}{6}N^3\)
Ex 2. \(\tfrac{1}{6}N^3 + 100N^{4/3} + 56\) \(\sim \tfrac{1}{6}N^3\)
Ex 3. \(\tfrac{1}{6}N^3 - \tfrac{1}{2}N^2 + \tfrac{1}{3}N\) \(\sim \tfrac{1}{6}N^3\)

Technical definition. \(f(N) \sim g(N)\) means \(\lim_{N \to \infty} f(N)/g(N) = 1\).

Part 3

Name It

Order of Growth

Part 2 ended with \(\sim \tfrac{1}{2}N^3\) array accesses. The \(\tfrac{1}{2}\) is machine-specific. The \(N^3\) is not.

Definition. If \(T(N) \sim c\,g(N)\) for some constant \(c > 0\), the order of growth of \(T(N)\) is \(g(N)\).

Drop the leading coefficient — it moves with the machine, the compiler, the JVM. Drop the lower-order terms — the leading power swamps them.

\[\tfrac{1}{2}N^3 \;\longrightarrow\; N^3 \qquad\qquad \tfrac{1}{2}N^2 - \tfrac{1}{2}N \;\longrightarrow\; N^2\]

Seven Functions Cover It

Good news. Almost every algorithm you will meet has one of these seven orders of growth.

\[1 \;<\; \log N \;<\; N \;<\; N\log N \;<\; N^2 \;<\; N^3 \;<\; 2^N\]

Common Orders of Growth

order name code framework example \(T(2N)/T(N)\)
\(1\) constant a statement add two numbers \(1\)
\(\log N\) logarithmic halve each step binary search \(\approx 1\)
\(N\) linear one loop find the maximum \(2\)
\(N \log N\) linearithmic divide and conquer mergesort \(\approx 2\)
\(N^2\) quadratic double loop check all pairs \(4\)
\(N^3\) cubic triple loop check all triples \(8\)
\(2^N\) exponential exhaustive search check all subsets \(T(N)\)

The last column is the one we measured in Part 1.

Big O

\(T(N)\) is \(O(g(N))\) when there are positive constants \(c\) and \(N_0\) with

\[T(N) \le c \cdot g(N) \quad \text{for all } N \ge N_0 .\]

In words: past some point, \(g\) is an upper bound on \(T\), up to a constant factor.

Common mistake. Reading big O as an approximate model. \(100N\) is honestly \(O(N^2)\) — true, and useless. Order of growth describes; big O bounds.

Your Turn

What is the order of growth of

\[T(N) = 5N^2 + 2^N + 10N \;?\]

\(2^N\) — the exponential term beats every polynomial term, no matter how large the polynomial’s coefficients are. By \(N = 20\) it is already \(99.8\%\) of the total.

Part 4

Compare

Can We Do Better?

Back to 3-Sum. The triple loop asks: for every \(i\), \(j\), \(k\) — is \(a_i + a_j + a_k = 0\)?

Turn it around. Pick a pair \(a_i, a_j\). The third number is forced:

\[a_k = -(a_i + a_j)\]

So we do not need a third loop. We need to look up whether that number is in the array.

Lookup Is the Guessing Game

Sort the array first. Then finding a number in it is exactly what we played at the start of class.

Binary search on \(N\) sorted items: at most \(1 + \lfloor \log_2 N \rfloor\) comparisons.

Trivial to Implement?

public static int binarySearch(int[] a, int key)
{
   int lo = 0, hi = a.length - 1;
   while (lo <= hi)
   {
      int mid = lo + (hi - lo) / 2;
      if      (key < a[mid]) hi = mid - 1;
      else if (key > a[mid]) lo = mid + 1;
      else return mid;
   }
   return -1;
}

First published in \(1946\). First correct one published in \(1962\). A bug in Java’s own Arrays.binarySearch() was found in \(2006\).

An \(N^2 \log N\) Algorithm for 3-Sum

Arrays.sort(b);                                  // step 1
for (int i = 0; i < N; i++)
   for (int j = i+1; j < N; j++)
   {
      int k = Arrays.binarySearch(b, -(b[i] + b[j]));   // step 2

   }

We derived \(N^2\) from the ratios. We predicted \(N^2 \log N\) from the code.

The Verdict

Same problem. Same machine. Same language. Same answer — both count \(500{,}153\) triples at \(N = 8{,}000\).

\(1.9\) hours versus \(17\) seconds.

Nobody bought a faster computer. Somebody picked a better order of growth.

Guiding Principle

A better order of growth beats a faster machine, and the gap widens with every doubling.

The measured gap at \(N = 32{,}000\) is \(402\times\). Extend both curves to \(N = 64{,}000\) and it projects to about \(800\times\).

Best, Average, Worst

The same algorithm can cost different amounts on different inputs.

  • Best case — the easiest input. A goal to aim for.
  • Worst case — the hardest input. A guarantee you can promise.
  • Average case — expected cost on random input. A prediction.

Which of these does a customer care about?

Now You Do It

Sum \(1 + 2 + \cdots + n\)

Algorithm A

long sum = 0;
for (long i = 1;
     i <= n; i++)
   sum = sum + i;

Algorithm B

sum = 0;
for (long i = 1;
     i <= n; i++)
{
   for (long j = 1;
        j <= i; j++)
      sum = sum + 1;
}

Algorithm C

sum = n * (n + 1) / 2;

Order of growth for each? Which would you ship?
