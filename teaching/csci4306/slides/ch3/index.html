What Does B Know?

B receives two segments without position labels.

Can B infer whether the stream was ABCD or CDAB?

A. Yes, use arrival order.

B. No, either order is possible.

B. Arrival order is not enough. B needs each piece’s position in the stream.

TCP Carries Bytes

A TCP connection carries an ordered stream of bytes in each direction.

TCP may group those bytes into segments differently from the application’s writes.

Why Number Bytes?

How could TCP split ABCDEF into segments?

What stays the same when the boundaries move?

A. The bytes and their positions.

B. The contents of segment 2.

A. Byte positions identify the data even if segment boundaries change.

Can TCP Split a Message?

A chat client writes GO\n, then STOP\n. Here \n is one newline byte.

Vote: are these reads valid, or did TCP damage the messages?

Valid. Reads can split a message or combine messages. The application must find each newline.

Rebuild the Chat Messages

Each newline ends a message. Keep unfinished text for the next read.

Predict the completed message and the text left in the buffer.

Read returns Completed message Left in buffer
GO\nST GO ST
OP\n STOP Empty

The second read completes ST + OP\n. A read boundary is not a message boundary.

Our Trace Rules

  • The TCP connection is already established. All earlier bytes have arrived in order.
  • Segment lengths count payload bytes. There are no SYN or FIN flags in these traces.
  • Host B sends an ACK after each arrival and buffers out-of-order data.

These assumptions let you determine one answer at every step. Real TCP may delay some ACKs.

Sequence Numbers Must Know

Seq gives the number of the segment’s first payload byte.

For a segment with \(n\) payload bytes:

\[\text{last byte} = \text{Seq} + n - 1\]

\[\text{next new byte} = \text{Seq} + n\]

Seq = 1000, payload = 200 bytes: bytes 1000–1199. The next new segment starts at 1200.

Bytes or Characters?

Send café starting at Seq 9000. Its UTF-8 encoding is shown in hexadecimal.

What is the next new Seq: 9004 or 9005?

9005. Four characters occupy 5 bytes. TCP counts the encoded bytes, including both bytes of é.

Divide the Stream

Start at byte 1000. The next three segments hold 200, 100, and 150 bytes.

Call out the first and last byte of each segment before revealing it.

Did It Arrive?

Host A sends some data. Imagine that B sends no reply.

What message would let A distinguish delivery from loss?

B must send feedback. An acknowledgment (ACK) reports which data reached B.

One Reply Is Missing

Which reply tells A that all 300 bytes arrived?

A. “Segment 2 arrived.”

B. “All bytes through 1299 arrived.”

B. ACK 1300 reports the next needed byte. It covers all earlier bytes.

Cumulative ACKs Must Know

ACK = x means: “I have every earlier byte in order. Send byte x next.”

After bytes 1000–1199 arrive, Host B sends ACK 1200.

The ACK identifies the next needed byte. It covers all earlier bytes in this connection, even if an earlier ACK was lost.

An ACK confirms receipt by TCP. The receiving application may not have read those bytes yet.

In-Order Arrival

Host B initially expects byte 1000.

Predict the ACK after each data arrival. Then reveal B’s reply.

A Gap Holds the ACK

Host B has bytes 1000–1199. Bytes 1300–1449 arrive next.

Vote: ACK 1200 or ACK 1450? Explain what each would promise.

ACK 1200. Receiving later bytes does not fill the gap.

From ACK 1200 alone, Host A cannot tell which later bytes are buffered.

Deliver These Bytes?

The application is waiting for the next bytes of its stream.

Vote: give the application 1300–1449 now, or hold them?

A. Deliver them now.

B. Hold them until the gap fills.

B. Hold them for 1200–1299 to preserve byte order.

Filling the Gap

B holds 1000–1199 and 1300–1449. The gap now fills.

Predict: will the next ACK be 1300 or 1450? Why?

ACK 1450 covers all three segments. Host B can now deliver the buffered bytes in order.

When an ACK Is Lost

Both segments arrive. Only the second ACK reaches A before timeout.

Must A resend the first segment? Why?

No retransmission is needed. ACK 1300 covers bytes 1000–1299.

A Download Stalls

A 1500-byte game update has three 500-byte pieces. B expects 4000; the application reads available bytes immediately.

After pieces 1 and 3 arrive: how many bytes can the app read? Which ACK?

500 bytes; ACK 4500. Another 500 bytes are buffered beyond the gap.

The Download Continues

B has delivered 4000–4499 and buffered 5000–5499. Piece 2 now arrives.

Predict the new ACK and how many additional bytes the app can read.

ACK 5500; 1000 additional bytes. The missing piece and the buffered piece are now available in order.

Your Turn: Meaning

Host A receives ACK 5200. Which statement must be true?

  • A. Byte 5200 has arrived at Host B.
  • B. All earlier bytes have arrived in order at Host B.
  • C. Host B has no bytes beyond 5200 buffered.

B. The ACK does not tell you whether later bytes are buffered or whether the application has read the data.

Is Your Upload Saved?

The server’s TCP has received your project upload. The server application has not run yet.

Can the final TCP ACK justify displaying “Project saved”?

No. TCP confirms byte receipt. The application must confirm that it saved the file.

Find the Wrong Rule

B expects byte 1100. It has bytes 1000–1099 and 1200–1299.

“The largest byte received is 1299, so B should send ACK 1300.”

Discuss with a neighbor: which word or step makes this rule wrong?

ACK 1100. The ACK tracks the first missing byte. The largest received byte may lie beyond a gap.

Describe the range 1100–1199 that ACK 1300 would falsely claim had arrived.

Both Directions Reading

Each direction has its own byte sequence. Host A’s next byte is 70; Host B’s is 900. A sends one byte and B echoes it.

Direction Seq ACK Payload
A → B 70 900 1 byte
B → A 900 71 1 byte
A → B 71 901 0 bytes

B’s reply carries data and an ACK together. The final ACK has no payload, SYN, or FIN, so it consumes no sequence number.

Message Boundaries Reading

If you write AB and then CDEF to a TCP socket, the receiving application gets the ordered bytes ABCDEF.

One read might return ABC, followed by a read returning DEF. A successful read need not match one write or one TCP segment.

To separate application messages, define a delimiter, a fixed length, or a length field. TCP’s sequence numbers identify positions in the byte stream.

Build Reliable Delivery

Keep TCP’s byte numbers. For the next examples, A sends one data segment and waits for its ACK.

What could prevent A and B from finishing this exchange?

The data can be corrupted or lost. The ACK can also be corrupted, lost, or delayed.

At each failure, decide what information or action is missing. Assume later transmissions can succeed.

Warm-Up: Changed Bits

A bit error changes a character while the data is in transit.

Vote: does receiving the expected length prove the data is correct?

A. Yes, all 8 bytes arrived.

B. No, their values may have changed.

B. The values need an error-detection check.

Detect Corruption

Attach a checksum so B can check the received bits.

A failed check detects damage. Does it also supply the original data?

No. Another copy is needed. Some errors can go undetected; the checksum is not a repair code.

Protect the ACK Too

B sends ACK 3100, but corruption changes it to ACK 3000 on the way back.

Vote: is checking only data segments enough?

A. Yes; ACKs contain no application data.

B. No; A relies on the ACK’s fields.

B. ACKs need error detection too. A must not act on a segment whose checksum fails.

A damaged control message can prevent progress even when the data arrived correctly.

Confirm Receipt

B expects byte 3000. A sends 100 payload bytes.

Predict B’s ACK. What does that reply allow A to stop waiting for?

A valid ACK 3100 confirms receipt of the outstanding data. A can now continue with new data.

Your Turn: Failure

A protocol uses checksums and ACKs but has no timer. Its data segment is lost. The sender waits for an ACK before sending more. What happens next?

  • A. The checksum causes the sender to retry.
  • B. The receiver ACKs data it has not received.
  • C. The sender may wait forever.

C. No packet reaches the receiver, and no timer creates an event at the sender.

Keep a Copy?

You propose “send the data again” after a loss.

When can A safely release the saved data?

A. As soon as A sends it.

B. After a valid ACK covers it.

B. Keep a copy until acknowledged, so A can retransmit it.

Stop Waiting When?

A has a saved copy, but no ACK arrives. A needs an event that occurs even when the network is silent.

What should A do when its chosen deadline expires?

Retransmit and restart the timer. The timer supplies the event that a lost packet cannot supply.

A Data Segment Is Lost

A’s timer expires. Should the retry use Seq 3000 or Seq 3100?

Retry Seq 3000, with the same bytes. Restart the timer.

An ACK Is Lost

B receives bytes 3000–3099, but the ACK is lost.

Predict A’s next action. Does A know the data arrived?

A cannot tell what was lost. Should B deliver these bytes again?

Same Sender View

Only A’s observations are shown below.

Can A safely assume delivery in Case B without receiving an ACK?

No. A cannot distinguish the cases. Retrying must be safe even when B already has the data.

Fire Once or Twice?

An arcade game sends one four-byte ASCII command, FIRE, per shot.

Before revealing the sequence numbers: can payload text identify a retry?

No. Seq 3000 repeats the first shot’s bytes. Seq 3004 carries a new shot, even though the command is identical.

Reject the Duplicate

B already delivered 3000–3099 and expects 3100.

Vote: deliver again; discard silently; or discard and repeat the ACK?

The sequence number identifies the duplicate. Repeating the ACK lets Host A finish waiting.

Why ACK a Duplicate?

Suppose B recognizes a duplicate but sends no reply.

What keeps A retransmitting? Which message would stop it?

A still lacks a valid ACK. B should send ACK 3100 again, without delivering the data again.

A Timeout Can Be Early

Both data and ACK can be delayed. Nothing in this exchange is lost.

Does a timeout prove loss? What can it cost?

No. A needless retry uses capacity; byte numbers prevent duplicate delivery.

An Old ACK Arrives

A already received ACK 3100, then sent bytes 3100–3199. A second copy of the earlier ACK was delayed.

Can A release the new bytes? What ACK is it waiting for?

No: it needs ACK 3200. ACK 3100 confirms none of the new bytes.

Choose the Timeout

Start the timer at 0 ms. A successful data/ACK exchange takes 70 ms. Compare fixed deadlines of 40 ms and 100 ms.

Predict the first retry in each case.

What happens? 40 ms deadline 100 ms deadline
Nothing is lost Retry at 40 ms No retry
First data segment is lost Retry at 40 ms Retry at 100 ms

A short deadline can cause needless retries. A long deadline delays recovery when data is lost.

Recovery Tools Must Know

Name the mechanism for each row before revealing it.

What needs to happen? Mechanism
Detect damaged bits Checksum
Tell the sender what arrived Acknowledgment (ACK)
Recognize repeated data Sequence number + receiver state
Act when no valid ACK arrives Timer
Send another copy Retransmission from a saved copy

Together, these mechanisms recover from detected errors and loss when later transmissions succeed.

The rdt Versions Reading

NAK means negative acknowledgment: a request to retry.

Version What changes?
rdt1.0 Assume no bit errors or loss.
rdt2.0 Add a checksum, ACK/NAK, and retry.
rdt2.1 Sequence numbers detect duplicates.
rdt2.2 Numbered ACKs replace NAKs.
rdt3.0 Add a timer for lost data or ACKs.

ACK Conventions Reading

In the textbook’s rdt2.2/rdt3.0 examples, sequence numbers 0 and 1 label packets. ACK 0 acknowledges packet 0.

In TCP, sequence numbers label bytes. ACK 3100 identifies the next needed byte and cumulatively acknowledges all earlier bytes.

Before tracing a protocol, check what its numbers count and what its ACK promises. TCP’s byte-number rule does not apply to every reliable-transfer protocol.
