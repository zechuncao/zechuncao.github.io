Our Trace Rules

  • The TCP connection is already established. All earlier bytes have arrived in order.
  • Segment lengths count payload bytes. There are no SYN or FIN flags in these traces.
  • Host B sends an ACK after each arrival and buffers out-of-order data.

These assumptions let you determine one answer at every step. Real TCP may delay some ACKs.

Warm-Up: Who Receives It?

Three programs on your CloudLab VM share one address. A segment arrives for 10.10.1.4.

Vote: what in the segment decides which of the three receives it?

Not the address: all three share it. The transport header carries the answer.

Demultiplexing Must Know

Every UDP and TCP header begins with a source port and a destination port.

A UDP socket is named by two values: destination IP and destination port. Two senders writing to the same port reach one socket.

A TCP socket is named by four: source IP, source port, destination IP, destination port. Two senders reach two sockets.

Sorting arriving segments by those values is demultiplexing. Adding the ports on the way out is multiplexing.

UDP’s Checksum Must Know

Add the 16-bit words with end-around carry, then complement the sum. Here is a datagram carrying the four bytes FIRE.

Field Value Binary
source port 40000 1001110001000000
destination port 5000 0001001110001000
length 12 0000000000001100
FI 0x4649 0100011001001001
RE 0x5245 0101001001000101

Sum, carries wrapped into the low bit: 0100100001100011

Checksum, the complement of that sum: 1011011110011100

What the Check Misses

The receiver adds every word, the checksum included, and expects one result.

0100100001100011 + 1011011110011100 = 1111111111111111 — all ones. Anything else means the datagram is damaged.

Every one of the 80 single-bit flips in that datagram changes the result, so each one is caught.

But 64 pairs of flipped bits cancel and pass the check. A checksum is a cheap test, not a guarantee — and it never repairs anything.

Why UDP, and What It Costs

What you get

  • A port pair, so the right socket gets the data.
  • An optional checksum.
  • No handshake before the first byte.
  • No per-connection state at either end.

What you do not get

  • Any promise the datagram arrives.
  • Any promise about order.
  • Any suppression of duplicates.
  • Any limit on how fast you send.

Your transport has to supply the right-hand column itself.

The Service and the Channel

Reliable transfer is a layer. It offers two calls upward and uses two downward.

Everything that follows adds machinery between those four calls. The application’s two calls never change.

rdt1.0: A Perfect Channel

Assume the channel never flips a bit and never loses a packet. One state on each side; on every arrow the event is above the line and the action below.

No checksum, no ACK, no timer. Which assumption breaks first on a real link?

rdt2.0: Bit Errors

The channel can flip bits. Add a checksum, feedback from B, and a retransmission from a saved copy.

What must B send back, and what should A do if the news is bad?

An ACK says the packet arrived intact; a NAK asks for another copy.

rdt2.0 Has a Fatal Flaw

B sends an ACK, but the ACK itself is corrupted on the way back. A cannot read it.

Vote: can A recover by simply sending the packet again?

A. Yes; ACKs contain no application data.

B. No; A relies on the ACK’s fields.

B. A cannot act on feedback it cannot read, and it cannot ask B what happened.

A’s only remaining move is to resend — which means B may receive a second copy of data it already holds.

Fire Once or Twice?

An arcade game sends one four-byte command, FIRE, per shot. A resends after a garbled ACK.

Before the numbers are revealed: can B tell a retry from a second shot?

No. The bytes are identical. Only a number carried in the packet separates them.

rdt2.1: Sequence Numbers

Put a number in every packet. B has delivered Pkt 0 and expects Pkt 1.

Vote: deliver again; discard silently; or discard and repeat the ACK?

The number identifies the duplicate. One bit is enough: only one packet is ever outstanding, so 0 and 1 never collide.

rdt2.2: Drop the NAK

Suppose B recognizes a duplicate but sends no reply.

What keeps A retransmitting? Which message would stop it?

A still has no feedback. B sends a numbered ACK for the last packet it accepted; that repeat does the NAK’s job, so rdt2.2 drops the NAK.

rdt2.2: The Sender

\(\Lambda\) = no action. A corrupted ACK and an ACK 1 both mean: resend.

rdt2.2: The Receiver

Wait for 1 from below holds ACK 0, so its loop repeats ACK 0.

Alternating Bits

Only one packet is outstanding at a time, so one bit tells the new packet from the last one: 0, 1, 0, 1.

A repeated ACK 0 does the work of a NAK. A sender waiting for ACK 1 reads ACK 0, or any corrupted ACK, as “retry packet 1.”

Is the Link Busy?

A 100 Mbps link carries one 1500-byte segment, then waits a 30 ms round trip for the ACK.

Vote: about 1 in 20 of that round trip, or fewer than 1 in 200?

Fewer than 1 in 200. Sending one segment and waiting leaves the link idle for almost the whole round trip.

Link Utilization Must Know

Utilization is the fraction of time the sender is actually putting bits on the link.

\[U = \frac{L/R}{\text{RTT} + L/R}\]

\(L = 1500\) bytes \(= 12{,}000\) bits, and \(R = 10^{8}\) bits/sec, so \(L/R = 0.12\) ms.

\[U = \frac{0.12}{30 + 0.12} = 0.0040 = \mathbf{0.40\%}\]

The sender moves 398 kbps across a 100 Mbps link.

Does a Faster Link Help?

Replace the 100 Mbps link with 1 Gbps. The distance is the same, so the round trip is still 30 ms.

Vote: does utilization rise, stay the same, or fall?

It falls, to 0.04%. With \(R = 10^{9}\), \(L/R\) drops to \(0.012\) ms while RTT is unchanged, so \(U = 0.012/30.012\).

Throughput barely changes: 398 kbps before, 400 kbps now. Either way the sender puts one segment on the wire, then waits 30 ms for the ACK.

The same work is now measured against ten times the capacity. A faster link does not help a sender that spends the round trip waiting.

ACK Conventions Reading

In the textbook’s rdt2.2/rdt3.0 examples, sequence numbers 0 and 1 label packets. ACK 0 acknowledges packet 0.

In TCP, sequence numbers label bytes. ACK 3100 identifies the next needed byte and cumulatively acknowledges all earlier bytes.

Before tracing a protocol, check what its numbers count and what its ACK promises. TCP’s byte-number rule does not apply to every reliable-transfer protocol.

Send Three, Then Wait

Fill the Pipe

With \(N\) segments in flight, the busy time is multiplied by \(N\):

\[U = \frac{N \cdot L/R}{\text{RTT} + L/R} \qquad\text{so}\qquad N = \frac{\text{RTT} + L/R}{L/R} \ \text{gives} \ U = 1\]

\(N = 30.12 / 0.12 = \mathbf{251}\) segments keep this link busy for the whole round trip.

Those 251 segments hold 3.01 Mbit. Chapter 1 called this the bits in flight: \(R \times \text{RTT} = 10^{8} \times 0.030 = 3\) Mbit.

Why Not Send Everything?

Filling the pipe took 251 segments. A has thousands more queued behind them.

Vote: can A put them all on the wire and sort the losses out later, or must something hold it back?

Something has to hold it back. A must keep every unacknowledged segment in case it has to resend it, and B cannot stack up an unbounded run of arrivals ahead of a gap.

Both buffers are finite, so the number outstanding has to be capped — and not capped small, because under 251 on this link A is waiting with the wire idle again.

Pick a Deadline

Any fixed deadline is a guess. Five round trips one sender measured: set the timeout at 120 ms, at 310 ms, or neither?

Neither. 120 ms retries on the 300 ms sample; 310 ms recovers slowly from every loss. An early retry costs capacity, not correctness: the sequence number makes the second copy a duplicate.

Measure the Round Trip

A SampleRTT is the time from sending a segment to receiving the ACK that covers it.

TCP takes about one sample per round trip, not one per segment, and never samples a segment it retransmitted.

Smooth the Samples

One sample is noisy, so TCP keeps a running average and moves it a little toward each new value:

\[\text{EstimatedRTT} = (1-\alpha)\cdot\text{EstimatedRTT} + \alpha\cdot\text{SampleRTT}, \qquad \alpha = \tfrac{1}{8}\]

The estimate moves one eighth of the way toward each sample.

One Average Is Not Enough

Two connections report samples with the same average.

Vote: should both use the same timeout?

No. A deadline just above 100 ms is safe on the left and fires constantly on the right.

Measure the Variation

TCP keeps a second running average, of how far each sample fell from the estimate:

\[\text{DevRTT} = (1-\beta)\cdot\text{DevRTT} + \beta\cdot|\text{SampleRTT} - \text{EstimatedRTT}|, \qquad \beta = \tfrac{1}{4}\]

Use the EstimatedRTT from before this sample, then update it. On a steady path DevRTT stays near zero; on a jittery one it grows.

Timeout Interval Must Know

\[\text{TimeoutInterval} = \text{EstimatedRTT} + 4\cdot\text{DevRTT}\]

EstimatedRTT = 84 ms, DevRTT = 6 ms, and a sample of 100 ms arrives.

\(|100 - 84| = 16\), so \(\text{DevRTT} = 0.75(6) + 0.25(16) = 8.5\) ms, and \(\text{EstimatedRTT} = (7 \cdot 84 + 100)/8 = 86\) ms.

\[\text{TimeoutInterval} = 86 + 4(8.5) = \mathbf{120 \text{ ms}}\]

When It Times Out Anyway

A timeout usually means congestion, and retrying at the same pace would add to it.

What should a sender do with its deadline after a timeout?

Double it. After a timeout at 120 ms the next deadline is 240 ms, then 480 ms. The formula resumes the moment a fresh ACK gives a usable sample.

This also keeps a retransmission from being sampled: its ACK is ambiguous, because A cannot tell which copy it answers.

Fast Retransmit Must Know

A duplicate ACK repeats an ACK number the sender has already seen. Each one means a segment arrived that could not fill the gap.

The rule: on the third duplicate — a fourth ACK carrying the same number — resend that segment at once, without waiting for its timer.

Three duplicates rather than one, because reordering in the network produces one or two on its own. Three means a segment is missing, not late.

Why No NAK Reading

The textbook’s rdt2.0 answers a failed checksum with a NAK: “that packet was damaged, send it again.” TCP has no NAK.

A cumulative ACK that stops advancing already reports the problem: ACK 2000 arriving again says bytes from 2000 are still missing. A NAK would also need its own protection against loss and against arriving out of order.

Modern TCP can add selective acknowledgment (SACK, RFC 2018), an option that lists the ranges the receiver has buffered beyond the gap. It extends the ACK rather than replacing it.

A Stale ACK Reading

The network can hold a copy of an ACK and deliver it late. Suppose A has already received ACK 3100 and has since sent bytes 3100–3199, and then a delayed second copy of ACK 3100 arrives.

It is not news. An ACK names the next byte B expects, so ACK 3100 says nothing about bytes 3100–3199 no matter when it arrives; A is waiting for ACK 3200 and must keep its copy of the new bytes until that number appears.

This is why a sender acts on the ACK number and never on the arrival of an ACK. It is also why a duplicate ACK on its own means little, and why fast retransmit waits for three.

Sampling a Retry Reading

If A sends a segment, times out, resends it, and then an ACK arrives, A cannot tell which copy that ACK answers.

Measuring from the first send overstates the round trip; measuring from the retransmission understates it, and an estimate that shrinks after every loss produces a timeout that is too short, which causes more retransmissions.

TCP therefore ignores retransmitted segments when sampling, and relies on doubling the interval while no clean sample is available. This is Karn’s algorithm.

Agreeing to Connect

Chapter 2 priced the handshake at one round trip. This is what the round trip buys.

Before any byte moves, what must each side learn?

That the other side is willing — and willing now, not during some earlier attempt that has since been abandoned.

Where the other side’s numbering starts. Topic 1’s sequence numbers had to begin somewhere, and each direction picks its own starting value.

How much room the other side has. That number rides in every segment from here on, and it is the second half of tonight.

Two Messages: The Half-Open

Suppose a connection opened on two messages: a request, then an acceptance.

Two Messages: Stale Data

The same two messages, but this time the client really did connect, send, and finish.

Three-Way Handshake Must Know

The third segment is what the two-message versions lacked: it proves the client is real and current.

Your Turn: Handshake

A client with starting number 300 opens a connection to a server whose starting number is 9100.

Segment Flags seq ack
Client → server SYN 300 none
Server → client SYN, ACK 9100 301
Client → server ACK 301 9101

The client’s first data byte is 301.

SYN Flood

A server that allocates on the first segment can be made to allocate until it has nothing left.

What does an attacker send, and what does it never send?

SYNs, from forged addresses, and never the third segment. Each one leaves a half-open entry like the delayed copy two slides ago, except there are thousands a second, and the table fills.

Chapter 1 listed denial of service and IP spoofing as attacks the Internet was not built to resist. This is both at once, and the handshake is where they land.

SYN Cookies

If allocating on the SYN is the weakness, what should the server do instead?

Allocate nothing. The server answers the SYN and keeps no record of having done so.

It chooses its own starting number as a cookie: a hash of the two addresses, the two ports, and a secret only the server knows.

A real client returns that number plus one in its third segment. The server recomputes the hash; if it matches, the client completed a handshake, and only then are buffers allocated. A forged SYN costs the server one reply and nothing else.

Closing a Connection

Each side closes its own direction, so the teardown takes four segments rather than three.

TIME_WAIT

The client has sent its last ACK and has nothing further to do. It waits anyway, typically from 30 seconds to two minutes.

Why not release the connection at once?

Because that last ACK can be lost. The server would retransmit its FIN, and somebody has to be there to answer it.

The wait also lets stray segments of this connection die in the network before the same pair of ports can be reused — the duplicate-data failure again, which the handshake alone does not prevent.

The Receive Window

The sender’s window in topic 3 was limited by what the network could carry. A second limit comes from the receiver.

Flow Control Must Know

\[\text{rwnd} = \text{RcvBuffer} - (\text{LastByteRcvd} - \text{LastByteRead})\]

RcvBuffer is 6000 bytes. B has received in order through byte 24,500 and its application has read through byte 20,000.

Waiting in the buffer: \(24{,}500 - 20{,}000 = 4500\) bytes.

\[\text{rwnd} = 6000 - 4500 = \mathbf{1500 \text{ bytes}}\]

A then keeps \(\text{LastByteSent} - \text{LastByteAcked} \le 1500\). The receiver’s buffer cannot overflow, whatever the sender’s own window allows.

rwnd that B advertises \(10{,}000 - 6000\) = 4000

A Window of Zero Reading

When B’s application stops reading, the buffer fills and B advertises rwnd = 0. A must stop.

The trouble is what happens next. B sends segments only when it has data or an ACK to send, and a sender that has stopped produces neither. The application could drain the buffer and B would have no reason to say so, leaving A waiting forever on a window that is no longer closed.

TCP breaks the deadlock from the sender’s side: while rwnd is zero, A keeps sending one-byte segments. Each one draws an ACK, and every ACK carries the current rwnd, so A learns of the free space on its next probe rather than waiting to be told.

Connection States Reading

The names on the two trace figures are states in a machine each side runs.

The client opens with SYN SENT and reaches ESTAB on the SYNACK. Closing, it passes FIN_WAIT_1 after its own FIN, FIN_WAIT_2 after the server’s ACK, and TIME_WAIT after the server’s FIN, reaching CLOSED only when the wait expires.

The server begins at LISTEN, moves to SYN RCVD on the SYN and ESTAB on the third segment. When the client closes first, the server passes CLOSE_WAIT — where it may keep sending — and LAST_ACK after its own FIN.

The RST Flag Reading

A SYN arriving at a port with no process in LISTEN is answered with a segment carrying the RST flag: no socket here.

Chapter 2 showed you this already. Starting a TCP client before its server gave ConnectionRefusedError at once rather than a timeout, and the RST is why: the host answered, it simply had nothing listening.

That difference is what a port scanner reads. An open port answers SYNACK, a closed port answers RST, and a filtered port answers nothing at all — so silence and refusal mean different things.

A Random Start Reading

Nothing in topic 1 required byte numbering to start at zero, and TCP makes sure it does not.

If starting numbers were predictable, an attacker who could not see the connection could still guess the numbers in use and inject a segment the receiver would accept as genuine — the sequence number is the only thing marking a segment as belonging to this connection. Guessing it is the whole attack.

The second reason is the one TIME_WAIT also addresses: a connection reusing a pair of ports must not accept a segment left over from the previous connection on them. A fresh random start puts the old numbers outside the new window.

Warm-Up: Too Much Traffic

Flow control stopped A from overrunning B. Nothing yet stops many senders from overrunning a router. What happens there first?

A. They queue

B. They are dropped

C. The link speeds up

A, then B. Chapter 1 called the wait \(d_{\text{queue}}\) and left it unexplained. Tonight is where it comes from.

Congestion Is Not Loss

Congestion is too many sources sending too much data too fast for the network to handle. Loss is one of its symptoms, not its definition.

Nothing in the network tells a sender it is happening. No router sends a message, and no field in the segment reports it.

So a TCP sender has to infer congestion from what it can see — and then act on the inference without being told whether it was right.

Two Senders, One Router

Two connections cross one router. Its outgoing link runs at R = 100 Mbps and its buffer is unlimited, so nothing is ever dropped.

The Cost of a Full Link

Throughput stops at 50 Mbps per sender. The queue does not stop at anything.

When the Buffer Is Finite

Real routers have finite buffers, so packets really are dropped — and a dropped packet is retransmitted.

If the sender retransmits every loss, what does the router’s outgoing link now carry?

Original data plus copies. The offered load at the link is larger than the data the application wanted to move, so the useful share of 50 Mbps shrinks.

A sender that could somehow retransmit only genuine losses would still fill the link with copies, and would still get less than 50 Mbps of useful throughput.

The Cost of Retransmission

Topic 3 showed a timeout firing on a segment that was merely slow. Under load, that happens constantly.

Each premature timeout puts a second copy of a segment on a link that is already full. In the worst case the router carries two copies of every packet.

Half the link’s work is then wasted, and the useful throughput falls to \(R/4 = 25\) Mbps.

Second cost of congestion: the sender must retransmit to make up for loss, and needless retransmissions cost the link capacity that the real data needed.

Work Thrown Away

Now give the packets more than one hop, with four connections competing at two routers in turn.

The Three Costs

As load rises What it costs
Queues build at the router Delay climbs without bound
Packets are dropped and resent Link capacity spent on copies
A packet dies on a later hop Every earlier hop’s work wasted

None of these appears in a sender’s own measurements as “congestion”. All it ever sees is a slower round trip and a missing ACK.

Who Tells the Sender?

Vote: should the network report congestion, or should the sender work it out alone?

End-to-end is what TCP does: no help from the network, congestion inferred from loss and delay. It needs nothing from routers, which is why it could be deployed at all.

Network-assisted has routers mark or report. It is more direct, but it requires every router on the path to take part.

TCP chose end-to-end in 1988 and still runs that way by default. A network-assisted option exists and arrives at the end of tonight.

How Fast to Start?

A fresh connection knows nothing about the path or the bottleneck rate.

Vote: open at full speed, at one segment, or at a fixed middle rate?

A. Full speed

B. One segment

C. A fixed middle rate

B, but not for long. A fixed rate is wrong on every path that is not that rate, so TCP probes instead: raise until something breaks, back off, raise again.

The Congestion Window

Topic 3 gave the sender a window. Topic 4 gave the receiver a say in it. Now the network gets one.

\[\text{LastByteSent} - \text{LastByteAcked} \;\le\; \min(\text{cwnd},\ \text{rwnd})\]

rwnd comes from the receiver, in a header field, and is exact. cwnd is the sender’s own guess at what the network will carry, and nothing confirms it.

Sending roughly one window per round trip, the rate is about \(\text{cwnd}/\text{RTT}\). Changing cwnd is how a sender changes its speed.

AIMD

Why Halve It?

Increase by one, decrease by half. Why not increase by one and decrease by one?

Because the two jobs are not symmetric. Probing for spare capacity can afford to be slow and careful; getting out of the way of a congested link cannot.

Backing off by one segment at a time while a router is dropping would take hundreds of round trips to make any difference, and the queue builds the whole while.

Halving also makes competing connections converge to an equal share, which an additive decrease does not. That argument closes tonight.

Slow Start

At one segment per round trip, filling a fast path would take forever. So the opening phase doubles instead.

Round cwnd Segments sent
1 1 1
2 2 2
3 4 4
4 8 8

Every ACK adds one segment to cwnd, which doubles it each round trip. “Slow” names where it starts, not how it grows — this is the fastest TCP ever increases.

Your Turn: Slow Start

A client fetches a 30,000-byte object on a fresh connection. MSS is 1500 bytes, the round trip is 40 ms, nothing is lost, and the receiver’s window never binds.

Find Answer
Segments needed \(30{,}000 / 1500\) = 20
Sent in rounds 1–4 1, 2, 4, 8 = 15
Rounds in total 5: the last sends the remaining 5
Time to the last byte \(5 \times 40\) = 200 ms

A short transfer never leaves slow start, so its speed is set by the round trip, not by the link rate.

Leaving Slow Start

Doubling cannot go on, so TCP keeps a threshold: ssthresh.

Below ssthresh the window doubles each round trip. At or above it, the window grows by one segment per round trip — additive increase.

ssthresh is not a constant. It is set to half the window that was in use when congestion was last detected, so it records where trouble was found last time.

Two Ways to Lose

Topic 3 gave a sender two ways to learn a segment is gone. TCP treats them as different news.

Signal What it suggests cwnd becomes
Three duplicate ACKs Segments still flow; one hole Halved, then additive increase
Timeout Nothing is getting through 1 segment, then slow start

Both set ssthresh to half the window at the time. The difference is where cwnd restarts from — and a timeout restarts from the bottom because the evidence is so much worse.

Average Throughput Must Know

One connection alone on a bottleneck link saws between \(W/2\) and \(W\), so its average window is \(\tfrac{3}{4}W\).

\[\text{average throughput} \approx \frac{0.75 \cdot W \cdot \text{MSS}}{\text{RTT}}\]

A 10 Mbps bottleneck, MSS 1250 bytes, RTT 50 ms.

\(W = (10 \times 10^{6})(0.050) / 10{,}000 = \mathbf{50}\) segments, sawing between 25 and 50.

Average throughput \(= 0.75 \times 10 = \mathbf{7.5}\) Mbps: one connection leaves a quarter of the link idle.

Your Turn: Throughput

A connection has a 40 Mbps bottleneck to itself. MSS is 1000 bytes and the round trip is 20 ms.

Find Answer
Bits per segment \(1000 \times 8\) = 8000
Window \(W\) that fills the link \((40 \times 10^{6})(0.020)/8000\) = 100
Average throughput \(0.75 \times 40\) = 30 Mbps
Rounds to climb \(W/2 \to W\) 50, so \(50 \times 20\) = 1 second

The Bottleneck Link

The sawtooth only touches the link rate at its peak, so a link with no buffer is idle three quarters of the time.

Give the router a buffer of one bandwidth–delay product and the dip is covered: while cwnd is below \(W\), the queue drains and keeps the link busy.

Make the buffer much larger and the link is no faster, but every packet now waits behind a queue that never empties. Chapter 1’s \(d_{\text{queue}}\) becomes permanent — the condition has a name, bufferbloat.

This is why a congested home link can show hundreds of milliseconds of delay while still reporting its full download speed.

TCP is fair per connection, and nothing stops an application from opening more. A UDP sender that ignores loss entirely takes whatever it wants.

Signals Other Than Loss

Approach How the sender learns
Loss-based (classic TCP) Three duplicate ACKs, or a timeout
Network-assisted (ECN) A router marks two bits in the IP header; the receiver echoes the mark in its ACK

ECN needs routers, sender and receiver alike. Delay-based needs only the sender.

TCP CUBIC Reading

After a loss the window halves, and additive increase then needs \(W/2\) round trips to get back. On a fast path that is a long time to run below capacity.

CUBIC keeps the window that was in use when the loss happened, calls it \(W_{\max}\), and grows as a cubic function of the time since. Far below \(W_{\max}\) it climbs steeply; near \(W_{\max}\) it flattens and approaches carefully; past it, having found no loss, it accelerates again to probe for new capacity.

The bargain is the same, with a better-shaped increase: most of the recovery is quick, and the caution is spent only where the last loss was. CUBIC is the default in Linux.

Delay as a Signal Reading

A loss-based sender only learns of congestion once a queue is full, which means it causes the delay it then reacts to.

A delay-based sender watches instead. It keeps $ ext{RTT}{}$, the smallest round trip it has seen, as its estimate of the path with no queue. If measured throughput is close to $ ext{cwnd}/ ext{RTT}{}$, the packets are not queueing and the window may rise. If measured throughput falls well below it, the extra window is sitting in a buffer rather than moving data, and the window should come down. BBR works this way.

The difficulty is coexistence: a delay-based sender backs off as a queue builds, and a loss-based sender beside it does not, taking the space that was given up.

Long Fat Pipes Reading

To fill a link a sender needs a window of one bandwidth–delay product. On a 10 Gbps path with a 100 ms round trip, that is \(10^{10} imes 0.1 / 8 = 125\) MB in flight, which is about 83,000 segments of 1500 bytes.

Two problems follow. The 16-bit window field cannot express it, which is what the window scale option exists for. Worse, additive increase needs one round trip per segment to climb back to 83,000 after a loss — well over an hour of near-perfect conditions.

That arithmetic is why the classic sawtooth was replaced on fast paths. CUBIC’s shape and BBR’s different signal are both answers to it.

QUIC Reading

QUIC puts a transport inside an application, on top of UDP. Everything this chapter built — sequence numbers, acknowledgments, retransmission, the congestion window — is implemented in user space rather than in the kernel’s TCP.

It buys two things. Setup merges the handshake with the TLS exchange, so an encrypted connection opens in one round trip instead of chapter 2’s handshake-then-TLS sequence. And one QUIC connection carries several streams, each acknowledged and retransmitted on its own, so a loss on one no longer stalls the rest.

The reasoning does not change. QUIC’s congestion control is the same AIMD family, against the same three costs.
